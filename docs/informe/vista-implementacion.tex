La Figura \ref{fig:vista_impl} muestra, con un diagrama de deployment UML \cite{Ambysoft2018}, los artefactos de la Tabla \ref{tab:ejecutables}, el entorno de ejecución en que corre cada uno y las dependencias entre ellos. \begin{itemize}
    \item Dentro del EAR, \texttt{carga-uy-web} depende de \texttt{carga-uy-ejb}, y este de \texttt{carga-uy-datos}.
    \item El frontend web y la aplicación móvil consumen la API REST del EAR. El frontend redirige las llamadas a \texttt{/api} hacia el componente central.
    \item El nodo de tracking publica en la cola \texttt{queue\_tracking} del broker, con TLS. El EAR la consume con un adaptador de recursos de WildFly configurado hacia ese broker.
    \item El EAR accede a PostgreSQL mediante el \textit{datasource} \texttt{CargaUyDS}, a MongoDB mediante su controlador y al directorio LDAP por LDAPS.
    \item El EAR consume Usuario gub.uy (OpenID Connect), la PDI (SOAP), el servicio de rutas y el nodo de balanzas por HTTPS, y el servidor de correo por SMTP.
    \item El EAR y los nodos periféricos envían su telemetría a la Plataforma de Observabilidad.
\end{itemize}

\subsection{Empaquetado}

Todos los componentes se distribuyen como imágenes de contenedor (R13). El componente central se construye en dos etapas: la primera compila el proyecto con Maven y la segunda configura WildFly 41 con el controlador de PostgreSQL, el \textit{datasource}, la conexión al broker de mensajería y MicroProfile Fault Tolerance, y despliega el EAR. El nodo de tracking también se construye en dos etapas y corre sobre la imagen de Java 24. PostgreSQL con PostGIS, MongoDB, el broker de mensajería, el directorio LDAP, el nodo de balanzas, el suplantador de la PDI y la Plataforma de Observabilidad corren cada uno en su contenedor. Un archivo de Docker Compose levanta el entorno completo con un único comando documentado en el README.

La configuración sensible (credenciales de gub.uy, secreto de los tokens de sesión, credenciales de la base de datos, de MongoDB, del directorio LDAP y de la mensajería, y la clave del servicio de rutas) se pasa por variables de entorno desde un archivo \texttt{.env} que no se sube al repositorio (R11).

\subsection{Integración Continua}

El repositorio del grupo tiene un pipeline de GitHub Actions que se ejecuta en cada \textit{pull request} y en cada cambio en la rama principal. El pipeline compila todos los componentes, corre las pruebas automatizadas, ejecuta el análisis estático de calidad del código y construye las imágenes de contenedor. El análisis estático usa PMD y SpotBugs en los módulos Java, ESLint en el frontend y Android Lint en la aplicación móvil. El pipeline debe estar en estado exitoso al momento de la entrega final (R17).
